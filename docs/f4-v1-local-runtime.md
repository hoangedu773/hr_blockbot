# PhoBERT F4 V1 local integration

OFF/default uses the exact-skills baseline without KPI. The initial implementation session could not install/load the model because RAM failed the conservative 2.5GiB headroom check. The 01/11/2026 follow-up passed repeated preflight and exercised the pinned real CPU model plus the real CRM browser chain in an isolated local environment. This is technical integration evidence, not an approved quality benchmark; independent human labels and the optimal coefficient remain pending. Mock tests alone are never real-model acceptance evidence.

## Boundaries

- One Node orchestrator serves initial assignment and replacement. Authorization V1, canonical reporting/scope and lifecycle eligibility are checked before sending minimal skill/task projections and rechecked after model execution. User identity, names, contact/bank data, grants and scope mapping are not part of the worker contract. An additional conservative text-content gate avoids sending obvious contact/HR identifiers; it is not a general PII detector.
- Only aliases c0/c1/etc cross the worker boundary; returned aliases, skill pairs, scores, model revision and request ID are validated. Unknown IDs or malformed responses cause labelled baseline fallback, never an assignment.
- Workload is the count of current scoped responsibilities and only breaks score ties. Incoming handover reservations are displayed separately. No evaluations/KPI are read or written by F4.
- Missing requirements/all candidate skills -> INSUFFICIENT_DATA/manual. More than200 candidates -> CAPACITY_EXCEEDED/manual rather than a silently truncated topK. Missing model/selected coefficient/worker failures -> MODEL_UNAVAILABLE + BASELINE_FALLBACK. Client cannot set mode, scope or coefficient.
- Human assignment/review, CAS, consent, handover and audit stay in the existing CRM endpoints. No chatbot tool/write is added. The follow-up readiness fix changes only internal Authorization HTTP routing to `trust_env=False` (TLS verification remains enabled); external answer-provider routing, Jev SHADOW decisions and business authorization checks remain unchanged. The synthetic Jev fixture provisions its callback client during lifespan, not within its unchanged 500ms analysis budget.

## Dedicated worker prerequisites

Source: app/f4_gateway.py, separate process on loopback port8001; do not mount in the existing chatbot or change Render. requirements-f4.txt contains selected top-level dependency pins, not a full transitive lock. A separate Windows/Python3.13.5 CPU environment was installed and checked with pip check, forward and browser E2E in the follow-up. Preserve the installation report and resolved versions; this does not guarantee another machine or approve production security. Never install/download/load before resource preflight passes.

1. Run scripts/prepare_f4.py --destination <private-local-cache> without --download for a RAM/disk report. Guard: >=2.5GiB available RAM and >=4GiB free disk, an engineering safety budget rather than a measured model minimum.
2. On a suitable CPU environment, create a separate venv, validate/install requirements-f4.txt using the official PyTorch CPU index/PyPI, record the resolved versions. Do not alter .venv-authz-v1 or the running AI environment. If enforcing wheel-only installation, allow only py-vncorenlp's official pure-Python sdist (`--only-binary=:all: --no-binary=py-vncorenlp`); its pinned release has no upstream wheel. Configure `JAVA_HOME` for the worker process to a compatible JDK; benchmark and B01 real E2E used JDK24. A `java.exe` shim on PATH alone did not make the B01 worker usable: warm-up returned503 without JAVA_HOME and passed with the tested JDK. Do not change machine-wide variables or copy JDK binaries into Git. No compiler or Windows installation change was needed on the exercised host.
3. After passing resource preflight, explicit --download fetches vinai/phobert-base revision01daacda68afe13d83023d16ec647239e344a1e6 and VnCoreNLP wseg assets at commit62bbc58fe5d113c898eae112656be97dcf50b3a0 from official public sources. No token is needed. Existing completed cache is retained; partial-download reconciliation is not yet implemented, so inspect partial files rather than overwriting/removing them blindly.
4. Setup writes SHA256 artifact manifests. F4_MODEL_DIR/F4_SEGMENTER_DIR point to those directories. Runtime checks manifests and uses local_files_only with remote-code execution disabled. No inference-time downloads; VnCoreNLP's auto-downloader is never called.
5. Set a dedicated F4_SERVICE_KEY (>=32chars) on the local worker and Node. From apps/ai-service, launch the worker using its own Python: python -m uvicorn app.f4_gateway:app --host 127.0.0.1 --port 8001. Do not use credentials from another system. On Windows, set JAVA_HOME only for this process to an existing JDK containing bin/server/jvm.dll; a java.exe PATH shim alone did not permit PyJNIus discovery on the exercised host. Do not edit system environment/registry or install a JDK globally as a workaround.
6. Run tests/test_f4.py with RUN_F4_REAL=1 in the dedicated environment for actual tokenizer/segmentation/forward/padding/truncation checks. Missing artifacts are a failure, not a substitute mock.

Node optional server configuration: F4_MODE=PHOBERT, F4_WORKER_ORIGIN=http://127.0.0.1:8001, F4_SERVICE_KEY, F4_SEMANTIC_WEIGHT. A production coefficient is not preselected: obtain it from independently labelled development data. Baseline OFF requires no worker, key or coefficient. The worker HTTP deadline remains8seconds. One actual CPU smoke measured ~14.67s constructor load, ~709ms first two-text forward and ~524-732ms for three two-candidate synthetic ranking calls; these are small smoke samples, not an SLA or official pilot benchmark. Process peak including embedded JVM was959,651,840bytes. Capacity1 retains its permit until actual computation ends; Node never accepts late results after timeout.

For local model demo, explicitly warm the owned worker with a service-authenticated synthetic /rank before opening CRM suggestions; /health must then show loaded:true. The real browser harness already does this warm-up before the Node8s path. A cold user request can legitimately return labelled baseline fallback while the model finishes loading; do not raise Node's deadline or call that cold request a successful PhoBERT recommendation. Startup/readiness and resource management need a deployment-specific design before production.

Pytest on this Windows/JDK24/PyJNIus host printed `Windows fatal exception: access violation` at JVM initialization even though all7 F4 tests continued and exited0. A minimal JNI probe reproduced the diagnostic only with Python faulthandler enabled; both variants completed Java assertions and exited0. It was not suppressed or solved by disabling the pytest plugin. Retain this diagnostic, distinguish it from a process crash, and qualify long-running production JVM compatibility separately. The standalone real forward and owned browser worker completed successfully.

## Pilot and acceptance

eval/f4-pilot.json has20 synthetic tasks and10 candidates/task, dev/test scenario groups and deliberately empty judgments. Keep that source unchanged. Rubric/protocol are proposals, not company policy. The evaluation phase now requires two separate complete human packets, their exact source/protocol/file hashes and an externally completed approval manifest with actual rubric/label approval references and timestamps. Merely editing dataset status strings cannot open evaluation. Disagreement remains blocked, not automatically adjudicated. See f4-pilot-review-guide.md and f4-evaluation-checklists.md. evaluate_f4.py --check-only verifies evidence without model/metrics; official execution requires approved evidence plus resources, selects alpha using dev only, then reports held-out baseline, pure PhoBERT and selected combination including worse cases. No official pilot results exist yet. Timing separates baseline/semantic cores from model load, not Web/API latency; peak RSS includes the in-process JVM/model, not standalone baseline memory. Retain actual artifacts and source/library fingerprints before scientific acceptance.

Normal Python/API tests use explicit synthetic encoders/HTTP responses, not PhoBERT evidence. The mandatory actual-model test is separate and skipped unless RUN_F4_REAL=1. Real Web->Node->Python->revalidation->manager->assignment acceptance: RUN_F4_REAL=1, F4_REAL_PYTHON, F4_MODEL_DIR, F4_SEGMENTER_DIR, F4_SEMANTIC_WEIGHT then node apps/web/test/f4-real.integration.mjs. That script owns its worker, uses synthetic CRM/Mongo fixtures, never substitutes an encoder, and fails missing prerequisites. It passed in the follow-up with experimental alpha0.5, neither optimal nor a default. The full workflow took~56.95s including model warm-up, logins and CRM/report/handover/profile regression steps; that is not individual suggestion latency.

Official F4 quality acceptance remains blocked by approved rubric, independent human labels/dev coefficient and the controlled baseline-vs-PhoBERT benchmark. Revalidate resource/install checks and real forward/browser gates on each target environment. The follow-up repaired and reran Jev SHADOW/full API; its report supersedes the historical readiness failure, not the unrun quality benchmark. No F1>=85% claim, fine-tuning, deployment or real employee data use is authorized by this implementation.

Follow-up approval permits an explicitly declared experimental `F4_SEMANTIC_WEIGHT` solely for real-model integration testing before benchmark labels are available. This does not select an optimal coefficient, enable PHOBERT by default, or waive resource/real-weight requirements. Do not use test integration output as quality evidence. Technical integration still requires explicit opt-in, a separate Python runtime, pinned real assets and the declared integration-only coefficient; official benchmark still requires independent labels.

Human annotation preparation: see [f4-pilot-review-guide.md](f4-pilot-review-guide.md). `eval/prepare_f4_review.py` exports two unlabelled, blinded JSON packets without touching the 20x10 source pilot. Official evaluation remains blocked until actual rubric approval and two independent human judgments exist.
